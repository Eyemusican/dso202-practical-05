# Task 6: ConfigMap hash and rollout chain

I changed the text in overlays/dev/index.html. That changed what Kustomize's ConfigMap generator produces, since the generator hashes the file's content into the ConfigMap's name, a different file means a different hash, so a brand new ConfigMap name, web-content-d7fdtd4b7b instead of web-content-9h599mhf86. Kustomize also rewrites every place that referenced the old ConfigMap name, so the Deployment's volume block automatically pointed at the new name too. That counts as a real change to the Deployment's pod template, which is what actually triggers Kubernetes to do a rolling update, kill the old Pod and start a new one with the updated volume reference. The old ConfigMap wasn't deleted anywhere in this, it's still sitting in the namespace unused, which is exactly what makes it possible to go back to the previous version if needed.
